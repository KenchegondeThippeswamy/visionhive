# Phase 8: Helm chart for VisionHive

Goal: turn the plain manifests of Phase 7 into one Helm chart with a values file per environment, then practise install, upgrade, rollback and the safety checks that make a chart trustworthy.
Done when: `./scripts/helm-check.sh` says ALL GOOD, the chart runs on Minikube, you rolled a bad release back with one command, and CI checks the chart on every pull request.
Cost: nothing. It all runs on your laptop.

## 1. What you are building
| File | Purpose |
|---|---|
| `helm/visionhive/Chart.yaml` | Name and version of the chart |
| `values.yaml` | Safe defaults (Minikube style) |
| `values-minikube.yaml` | Local cluster: images built inside Minikube, LocalStack and PostgreSQL in the cluster |
| `values-dev.yaml`, `values-qa.yaml`, `values-prod.yaml` | EKS environments: ECR images, real S3, SQS and RDS, IAM role annotations (IRSA), ALB ingress, zone spreading |
| `values.schema.json` | Rejects wrong types before anything is deployed |
| `templates/deployments.yaml` | One Deployment per service, generated by a loop over `services:` |
| `templates/services.yaml`, `hpa.yaml`, `pdb.yaml`, `serviceaccounts.yaml`, `ingress.yaml` | The rest of the objects, switched by values |
| `templates/postgres.yaml`, `localstack.yaml` | Local-only dependencies, off on EKS (`enabled: false`) |
| `templates/servicemonitor.yaml` | Prometheus scraping, off until Phase 12 |
| `templates/_helpers.tpl` | Shared labels and the image-name builder (the tag is mandatory) |
| `scripts/helm-check.sh` | Lint, render and schema-check every values file |
| `scripts/helm-up.sh`, `helm-down.sh` | Deploy to and remove from Minikube |
| `.github/workflows/helm-ci.yml` | Runs the check on every pull request that touches the chart |

Design points worth remembering:
- **Environments are only values files.** The templates never change between Minikube and EKS.
- **No secrets in the chart.** The database password and the fake LocalStack keys come from Secrets that must already exist (`database.existingSecret`, `aws.existingSecret`). On EKS, External Secrets creates `db-credentials` from the RDS secret in Phase 9.
- **The HPA owns the replica count.** When it is enabled, the Deployment has no `replicas:` line, otherwise every upgrade would fight the autoscaler.
- **A config checksum annotation** on the pods makes them restart when the ConfigMap changes (Phase 7 did not do that).
- **The image tag is required.** Rendering `values-dev.yaml` without a tag fails with a clear message, so a missing tag can never deploy `latest` by accident.

## 2. Install Helm (once)
Read the script first, then run it:
```bash
curl -fsSL -o get_helm.sh https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-4
less get_helm.sh
chmod 700 get_helm.sh && ./get_helm.sh
helm version --short
```
The chart works with Helm 3 and Helm 4. Helm 4 is the current stable release. The checks use kubeconform: install it, or let the script use its Docker image (you already have Docker).

## 3. Add the files
Stand in the repo root. Do **not** use a file manager's "Extract here". Do **not** add `-d`:
```bash
cd ~/Downloads/visionhive
git checkout dev && git pull
git checkout -b feature/phase8-helm
unzip -o ~/Downloads/visionhive-phase8.zip
ls helm/visionhive helm/visionhive/templates scripts
git status --short
```
Expected: `helm/visionhive` contains `Chart.yaml`, the values files, `files/` and `templates/`. `git status --short` lists only new files (`helm/`, three scripts, a workflow, a guide). There must be no `visionhive-phase8` folder inside the repo. If there is, run `cp -a visionhive-phase8/. ./ && rm -rf visionhive-phase8`.

## 4. Check the chart offline
```bash
./scripts/helm-check.sh
```
You should see four blocks (minikube, dev, qa, prod) each ending with `Valid: N, Invalid: 0`, and `ALL GOOD` at the end. A lint notice that says "icon is recommended" is fine.
Look at what the chart produces:
```bash
helm template visionhive helm/visionhive -n visionhive -f helm/visionhive/values-minikube.yaml | less
helm template visionhive helm/visionhive -f helm/visionhive/values-dev.yaml --set image.tag=abc1234 | grep -E "image:|role-arn|ingressClassName"
diff <(helm template v helm/visionhive -f helm/visionhive/values-qa.yaml --set image.tag=x) <(helm template v helm/visionhive -f helm/visionhive/values-prod.yaml --set image.tag=x)
```
The last command shows exactly what differs between qa and prod.

## 5. Deploy on Minikube
Only one copy of the app can run at a time:
```bash
make down                       # stop the Docker Compose stack if it is running
./scripts/k8s-down.sh           # remove the Phase 7 deployment if present
./scripts/helm-up.sh
./scripts/k8s-test.sh
```
`helm-up.sh` starts Minikube, builds the images inside it, creates the Secrets, and runs `helm upgrade --install`. The test must end with `"status": "done"`. Explore:
```bash
helm -n visionhive list
helm -n visionhive status visionhive
helm -n visionhive get values visionhive
helm -n visionhive get manifest visionhive | less
kubectl -n visionhive get all
```

## 6. Upgrade and roll back
```bash
helm -n visionhive upgrade visionhive helm/visionhive -f helm/visionhive/values-minikube.yaml --reuse-values --set config.processSeconds=2
helm -n visionhive history visionhive
kubectl -n visionhive get pods
helm -n visionhive rollback visionhive 1
helm -n visionhive history visionhive
```
After the upgrade the pods restart by themselves, because the ConfigMap checksum changed. After the rollback there is a new revision (a rollback is a new revision that copies an old one).

## 7. Break-fix labs (write each in docs/incidents/)
1. **Wrong value type.** `helm lint helm/visionhive -f helm/visionhive/values-minikube.yaml --set services.api-gateway.replicas=two`. The schema rejects it before any cluster is touched. Also try `--set services.api-gateway.hpa.targetCPU=250`.
2. **Missing image tag.** `helm template v helm/visionhive -f helm/visionhive/values-dev.yaml`. Read the error from the `required` guard.
3. **Bad release and rollback.** `helm -n visionhive upgrade visionhive helm/visionhive -f helm/visionhive/values-minikube.yaml --set image.tag=nope --wait --timeout 90s`. It times out, the release shows `failed`, and the old pods are still serving (rolling update). Roll back with `helm -n visionhive rollback visionhive`. Then repeat with `--rollback-on-failure` added (Helm 4; the same idea is called `--atomic` in Helm 3) and watch Helm roll back by itself.
4. **ConfigMap change.** Show that changing `config.processSeconds` restarts the pods (the checksum annotation) while changing nothing restarts nothing.
5. **Environment drift.** Run the diff between `values-qa.yaml` and `values-prod.yaml` and explain each line.

## 8. Helm versus Kustomize (interview answer)
| | Helm | Kustomize |
|---|---|---|
| Idea | Templates plus values, packaged as a chart | Plain YAML, patched per environment |
| Releases | Tracked: history, rollback | Not tracked: kubectl apply only |
| Logic | Loops and conditions (powerful, harder to read) | None (simpler, less flexible) |
| Sharing | Charts can be published and versioned | Folders in Git |
| Used here | The application chart, Phase 10 Argo CD source | Phase 7 manifests (kept for comparison) |

## 9. CI and pull request
```bash
cd ~/Downloads/visionhive
git status --short
git add -A
git commit -m "feat: helm chart with values per environment"
git push -u origin feature/phase8-helm
gh pr create --base dev --head feature/phase8-helm --title "feat: helm chart" --body "Chart, values per environment, checks, CI"
gh pr checks --watch
```
The `helm-ci` workflow runs `helm-check.sh` on GitHub (Helm is preinstalled on its runners, and kubeconform runs from its Docker image). Merge when green. If the kubeconform image tag cannot be pulled, install kubeconform in the workflow instead, or tell me the error.

## 10. Verify, then clean up
```bash
./scripts/verify-phase8.sh
./scripts/helm-down.sh --stop
```

## 11. What changes for EKS (Phase 9)
`values-dev.yaml` is already written for it: ECR images, empty S3 and SQS endpoints (so boto3 uses real AWS), the RDS endpoint and the `visionhive_admin` user, IAM role annotations named `visionhive-dev-irsa-<service>` (Phase 9 creates those roles), an ALB ingress, zone spreading, and no LocalStack or PostgreSQL. The only value CI must supply is `image.tag`.
